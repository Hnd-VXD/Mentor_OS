# Bootable Mentor audit: what assumes the VM and Mentor.exe

> **Status (2026-10-18): kept for the non-VM release.** The owner parked the rest until a bootable
> Mentor (live USB / installer) is being built; start that work from this list, highest risk first.
> Done so far: **#1 shared clipboard**, fixed in update 18.10.26.01 (`mentor-clipboard` ends quietly
> without its port, `mentor doctor` skips the check; the doctor's traceback line fixed too). Mark each
> row done here as it is fixed.

2026-10-18. A read-only audit of Mentor's own files in `distro/rootfs` (plus `build/build.sh`,
`distro/customize.sh`, `distro/packages.x86_64`). The question for each piece: **what happens on a real PC
with no QEMU, no Mentor.exe and no virtio ports**, and what a bootable Mentor would need instead.
No code was changed.

**How it was checked.** By reading the code, and by booting the release image 17.10.26.14
(`out/release/new2/mentor.qcow2`, version 202610172214) headless under plain QEMU with *none* of
Mentor.exe's ports: no `org.mentor.clipboard`, `org.mentor.control` or `org.mentor.host`, no
`-fw_cfg opt/mentor/scale`, no sound card. Only a guest-agent port to drive it (a throwaway overlay in
the session scratchpad; the user's Mentor on 47811 was not touched). That is the closest a VM gets to
"no host". It still has virtio disk/net/GPU, so the hardware rows (firmware, GPU, Secure Boot, ESP) are
from reading, not from a test.

**Result in one line.** Most of the host link already steps aside quietly. **One thing breaks on day one:
the shared clipboard crashes at login, `mentor doctor` then reports two BROKEN parts, and mentor-watch
raises a red card** (seen in the test VM). The bigger gaps are the safety nets: restore points and the
Repair start exist only through Mentor.exe. On a real PC they are simply gone, and the agent is still
told they are there.

## Ranked table

Risk: **High** = a false red card, a broken promise to the user, or no way back after a bad change.
**Medium** = wrong behaviour or a misleading answer the user will hit. **Low** = cosmetic or a small cost.
**None** = steps aside already.

## What already works well

The host link's design (udev rule + `ConditionPathExists` + "Either half works without the other") is the
pattern to copy. mentor-host-link, mentor-volume, mentor-hello, qemu-guest-agent, tell_host and the scale code
all do nothing quietly with no port. In the headless VM with no Mentor.exe ports, `systemctl --failed` was
empty.

## Suggested order

1. **Now, small and safe in the VM too:** #1 (clipboard quiet + doctor), #10 and #11 (switch/key/game mouse
   only with a control port; `window_mode` without `O_CREAT`). These remove the false red card and the
   do-nothing switch today; a VM started by an older or test launcher without ports benefits too.
2. **One fact for everything:** `/run/mentor/host` (#4), written at boot. With it: the agent's prompt, the dconf
   values in #8, #9, #12 and #14, and whether to show the launcher-only switches.
3. **Before a live USB:** #5 (hardware packages, a separate list), #3 (repair entry and boot counting), #7
   (automatic time zone), #8 (lock and idle).
4. **Before an installer:** #2 (snapshots: btrfs + snapper, or say plainly there are none), #6 (ESP/XBOOTLDR,
   Secure Boot), dual-boot clock (#7).

For "Split Mentor" (the side-by-side chat) and later features: build them in the extension / mentor-chat as
planned. A feature that needs Mentor.exe should check the port at start and leave nothing on screen without it
(rows 10 and 11 are what to avoid).
