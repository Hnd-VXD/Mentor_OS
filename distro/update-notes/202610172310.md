# Mentor update: the assistant recovers from its own small mistakes

## What is new

- When the assistant asks one of Mentor's tools for something in the wrong form, it is told what was wrong and tries again, instead of stopping in the middle of your request.
- The assistant's answers through the NVIDIA and OpenAI engines no longer stop when the model sends its request in an unusual form.

## Why

- Testing every tool with wrong arguments (a list where text belongs, "five" where a number belongs) found 90 cases where a tool ended with a Python error. With an API engine (mentor-agent) that ended the whole answer. `call_with_image` in mentor_tools.py now checks the arguments against each tool's schema first (`_checked_arguments`): "5" for a number, "true" for true and an enum value in other capitals are taken, a null counts as left out, the rest is refused with "NAME must be text. Call TOOL again with the right arguments." An error a tool did not expect comes back as "TOOL failed: ..." instead. TOOLS.md, "How it hangs together".
- Names that start with "-" were taken for options by the programs behind some tools (package_peek "-rf" made pacman read `--root f`). They now come after `--` (flatpak search, gnome-extensions), or are checked first (Flatpak app ids, package names). These run as the user, never as root; the root helper always checked its names.
- `timeout_seconds` of 0 meant "give up at once" for run_command and terminal_run, and "no limit at all" in the sandbox; 0 or less now means the usual time.
- mentor-agent: some OpenAI-compatible servers send a tool call's arguments as an object instead of JSON text; that ended the answer with a Python error. Both forms are read now, and they are sent back as JSON text.

## Check at the end

- `mentor verify` says every file of Mentor's is as it was built.
- `mentor call package_info '{"package": [1]}'` answers "package must be text. Call package_info again with the right arguments."
