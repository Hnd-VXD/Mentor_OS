# Mentor's desktop: what it is made of, and how to make it again

This is for the agent. It lists everything Mentor adds to or changes in GNOME, what the user is meant to see, where it is done, what of GNOME it leans on, and how to tell that it works. Use it when something of Mentor's has stopped working, and above all when GNOME moves to a new major version: the aim then is that the user has the same things they had before, even where they have to be made another way.

`mentor doctor` (tool: desktop_check) says which parts work right now. Start there.

## How it hangs together

- **mentor-chat** (`/usr/local/bin/mentor-chat`, GTK 4 and libadwaita, Python) is the assistant: one frameless window with no background.
- **The shell extension** (`/usr/share/gnome-shell/extensions/mentor@mentor.local/`) makes that window the desktop and adds Mentor's pieces to the shell. It is set up part by part (`_part` in `extension.js`); a part that fails is logged, left out and reported by `Status`, and the others carry on.
- **Dash to Panel** (package `gnome-shell-extension-dash-to-panel`) is the taskbar; **AppIndicator support** the tray icons. Both are other people's extensions and break on their own schedule.
- **No "Dash to Panel has been updated!"**: Dash to Panel announces itself whenever its version differs from the `extension-version` it stored, on a fresh install and after each upgrade. `mentor-taskbar-quiet.service` (a user oneshot before `graphical-session-pre.target`, script `/usr/local/lib/mentor/mentor-taskbar-quiet`) stores the version from its `metadata.json` before the shell starts. It cannot be done from Mentor's extension: GNOME enables Dash to Panel before it. When the notice comes at every login, or `mentor doctor` says `mentor-taskbar-quiet.service is off`: the service was switched off; REBUILD.md, "Step 2b", switches it on again and starts it at once (no logout needed).
- **Defaults** are in `/etc/dconf/db/local.d/00-mentor` (run `dconf update` after changing it): the enabled extensions, favourites, key bindings, wallpaper, dark style, animations on (held back by the extension where no graphics card draws the screen: "Animations" below).
- **The launcher on Windows** (Mentor.exe) talks to the system inside over two serial ports: `org.mentor.control` (start-up reports, full screen, restore points, the game mouse) and `org.mentor.clipboard` (text and files, and the window's full-screen state).

Inside `desktop` (class `DesktopLayer`) there is more that leans on the shell:

- **The start has worked**: when the assistant's window has drawn itself and the taskbar's panels exist, `/run/mentor/desktop-ok` is written. A start that tries a change is only kept if this file appears within three minutes (`mentor_boot.py`). If this part is broken, every upgrade is undone at the next start. That is the safety, not a fault: fix the part, not the check.
- **Waiting for the taskbar** (`_whenTaskbarUp`): Dash to Panel 74 sets itself up in steps and breaks for the session if the screen changes in the middle. So the scale and the report above wait for `global.dashToPanel.panels`. If Dash to Panel changes how it starts, this is where to look.
- **Sharp text** (`_matchHostScale`, `mentor scale`): the desktop takes the scale of the Windows screen (`/run/mentor/host-scale`, from the launcher). Not every scale fits every resolution (200% does not fit an odd height, as when the window is maximized at 2880x1659): `_supported_scales` asks mutter (`GetCurrentState`) which ones the mode takes, and the largest quarter step (125%, 150%…) not above the wanted one is used, so a maximized window on a 200% screen gets 150% instead of staying at 100%. It is set with mutter's `gdctl set --persistent`, which makes the shell ask "Keep these display settings?"; `_keepScale` answers that by finding the dialog among `Main.layoutManager.modalDialogGroup` and calling its `_onSuccess` (private). A scale the user picks in Settings is theirs (`_onScreenChanged`, `~/.config/mentor/scale`). After the window changes size (maximized, full screen), the shell shows the new size at 100% until the scale is set again; so the extension sets it itself (`_applyScale`: mutter's D-Bus `org.gnome.Mutter.DisplayConfig` `GetCurrentState` and `ApplyMonitorsConfig`, method 2 = persistent, the same rules as `mentor scale`) 0.1 s after the change: about 0.2 s of 100% instead of 1.2 s when it started `mentor scale` (measured 2026-10-17 with a VNC client asking QEMU for new sizes). When that fails, the log says `mentor: scaling directly failed (…)` and `mentor scale --keep` does it the old way. To check: `journalctl --user -b -o cat | grep "mentor: scaling"` (nothing is good), and after a resize `gdctl show` gives the host's scale. **No 100% at all with a whole scale** (2026-10-22, the user saw the 0.2 s on every first maximize or full screen): mutter (51) uses `org.gnome.desktop.interface scaling-factor` as the scale of every size it has not seen yet, so `_defaultScale` sets it to the wanted scale when that is whole (200%, 300%) and to 0 otherwise (150%: the 0.2 s stays, `_applyScale` mends it). Measured with a VNC client asking for new sizes and `GetCurrentState` every 50 ms: before, 1.0 for 0.22 s at each new size, then 2.0; after, 2.0 straight away. Changing the setting does not change the screen, and apps scale as before (a GTK 3 window on Wayland and on X11 reports scale 2 either way). Only when a launcher gave a scale (`/run/mentor/host-scale`): on a real computer the setting is left alone. Check: `gsettings get org.gnome.desktop.interface scaling-factor` gives `uint32 2` with a 200% Windows screen; a warning `mentor: could not set the default scale` in the journal if it could not be set. Mutter also remembers the scale of each size it has seen during a session, so from the second time the window takes a size there is no 100% even with 150%. What is still seen when the window changes size is QEMU stretching the old picture for a moment until the system has drawn at the new size: that is the window on Windows, not this system.
- **A conversation for each workspace**: `active-workspace-changed` tells mentor-chat (`mentor-chat --workspace N`).

## When GNOME moves to a new major version

The extension only loads on the versions in the `shell-version` list of its `metadata.json`. On another version the shell leaves it out, the start does not report itself, and the upgrade is undone three minutes later. So the order is:

1. **Before upgrading, read what changed.** In the sandbox, install the new `gnome-shell` and read the shell's own code for the things in the tables above (it is packed in `/usr/lib/gnome-shell/libshell-*.so`; `gresource extract` from `glib2-devel` gets a file out, e.g. `/org/gnome/shell/ui/appDisplay.js`). Check each private name this file mentions. The release notes and the extension porting guide (gjs.guide/extensions/upgrading) name the breaking changes.

## Mending one part, step by step

In the user's words: the taskbar is gone or disappeared; a part of the desktop is missing or disappeared; a switch or a menu is gone; the desktop looks wrong after an update; mentor doctor says something is broken; an extension error.

For a small model: do exactly this, one part at a time. **If, after one careful attempt, the check below still fails, or a step here no longer matches the system** (a class, a file, a function or a command GNOME changed): stop, tell the user in one sentence that the instructions for this part are out of date, and offer to report it (problem_report, AGENT.md): an update will bring instructions that fit. The part stays as GNOME draws it meanwhile.

**1. Find the part that is broken.**

```
mentor doctor
```

Lines about the assistant itself ("the assistant is running", "the assistant is the desktop" while the extension is ACTIVE, "errors of the assistant's") are ASSISTANT.md, "When it is broken", not this section; lines about a service that is off are REBUILD.md, "Step 2b"; the clipboard line is "The shared clipboard, for mending it" below. Each line starts with `ok`, `BROKEN`, or `WARN` for a small part that is gone (a yellow card, not a red one: mentor-watch's `doctor-minor`). A line `BROKEN part: NAME: MESSAGE` names a part of the extension and the error it stopped with. The same, with the place in the code:

```
journalctl -b -o cat _COMM=gnome-shell | grep -A8 'mentor: the part'
```

If `mentor doctor` says the extension's state is `OUT OF DATE`, the shell is a version the extension does not name: do step 1b first (a damaged `metadata.json` says the same), and only when `metadata.json` is as built read "When GNOME moves to a new major version" above. If it says `ERROR`, the whole file failed to load (a syntax error, or an import that no longer exists): `gnome-extensions info mentor@mentor.local` shows the error.

**1b. Is the extension still as it was built? Always look before step 2.**

```
mentor verify
cat ~/.local/share/mentor/notes.md
```

- `extension.js` or `metadata.json` listed as `changed` (or `missing`), and nothing in notes.md or `mentor journal -n 20` says it was changed on purpose: the file was damaged, **GNOME did not change**. Do not edit it and never `mentor verify --accept` it. Put it back as built, as root: `cp -a /etc/mentor/source/rootfs/usr/share/gnome-shell/extensions/mentor@mentor.local/FILE /usr/share/gnome-shell/extensions/mentor@mentor.local/FILE` for the one file `mentor verify` names (or the whole folder: the table "Putting the desktop's files back as built" below, first row), then step 6 (ask, then log out and in) and step 7. That is the whole fix; steps 2 to 5 are not needed.
- Listed as `accepted`, or `changed` with a note saying why: someone adapted it on purpose. Read the note, then go on with step 2 on the installed file.
- Not listed (as built) and a part is still broken: the shell changed under it (a GNOME update, `pacman -Q gnome-shell`). Go on with step 2.

**2. Read how the part is made.** The extension is one file, `/usr/share/gnome-shell/extensions/mentor@mentor.local/extension.js`. Every part is set up inside `enable()` like this, and nowhere else:

```js
this._part('app menus', () => {
    // ... set the part up; anything that throws here marks only this part as broken ...
    return () => { /* how to take it down again */ };
});
```

`_part(name, setUp)` runs `setUp` inside `try`, keeps what it returns for `disable()`, and records `ok` or `broken: MESSAGE` under the name, which is what `Status` and `mentor doctor` report. So a broken part never takes the others with it. Keep that shape: one `_part` per thing the user has, the taking-down returned from it.

**The desktop cannot be moved, hidden or closed by mistake.** **History is a window of its own** since 2026-10-20 (the user's wish: minimize and maximize as any program): an `Adw.Window` with a real `Adw.HeaderBar` (`show_history`, one at a time, `self.history_window`; Esc clears the search, then closes), in the taskbar under Mentor's icon. Every window of the assistant's program is taken for the desktop by `_adopt`, so the extension leaves the titles in `PLAIN_TITLES` ("History") as normal windows: without that, History became the desktop and the real one lost its place (tested). The title in `mentor-chat` and in `PLAIN_TITLES` must stay the same. A dialog inside the assistant (a picture, Suggestions) has its frame and header act as the window's title bar: on 2026-10-14 dragging History's header moved the whole desktop, and a right click offered its window menu (Move, Hide, Always on Top, Close). So: the dialogs have a plain header (`dialog_header` in `mentor-chat`, not `Adw.HeaderBar`); the shell shows no window menu for the desktop window (`showWindowMenuForWindow` of `Main.wm._windowMenuManager`, overridden in the `desktop` part); and whatever moves, resizes, minimizes or puts it above is undone at once (`_keepPlace`, `notify::minimized`, `notify::above` in `_adopt`). It does not even look moved while it is dragged (since 2026-10-19: dragging the dimmed space around a picture's preview or History moved the desktop with the mouse, `_keepPlace` put it back after each step, and it jittered). A dialog of the chat is a window attached to the desktop, and a drag around it is a move of the desktop that the window manager carries out; mutter 51 has no call to stop one once begun (a virtual Escape or button release from the extension did not end a real mouse's drag), and the chat never sees that press. So `_holdStill` (on `global.display` `grab-op-begin` for the desktop window) marks it held, and while it is, `_keepPlace` shifts the picture of the desktop and of its attached dialogs (`translation_x`, `translation_y` of their actors, `_shift`) back by as much as the window moved, in the same frame: on the screen nothing moves. `_letGo` (`grab-op-end`) puts the window back in its place and the shift to 0. `Status` counts both: `desktop_drags_held` (drags held still) and `desktop_put_back` (times the desktop was moved and put back the old way, which should stay 0). To check: open History, drag on the dark space beside it: nothing moves, and `desktop_drags_held` goes up.

**Which assistant window is which** (`_adopt`): the desktop window is titled "Mentor", the text box over the windows (Alt+Space) "Ask Mentor" (`ASK_TITLE`). Only a window with that title is floated (`_float`: above all, on every workspace, at the bottom); any other assistant window becomes the desktop, taking the place of one still known. It was told apart by "a desktop window is known already": on 2026-10-14 the assistant, started again by an update while its old window was still known here, was taken for the text box, and the desktop became a window that could be moved, always on top, with a window menu. A window with no title yet waits for it (`notify::title`). `Status` says `assistant_on_desktop` true only when the known window really is a desktop-type window (`mentor doctor`: "the assistant is the desktop").

The classes above `MentorExtension` in the file: `DesktopLayer` (the assistant as the desktop: finds the window whose application id is `org.mentor.Chat`, makes it a desktop-type window, sizes it to the work area, clears the windows away and brings them back, writes `/run/mentor/desktop-ok`), `ShellService` (the D-Bus object `/org/mentor/Shell`), `FullScreenToggle`, `TaskbarToggle` and `Indicator` (the switches in the system menu), `AskProvider` (the search result).

**3. Find what changed in the shell.** The error names what is missing (`X is not a function`, `X is undefined`, `Cannot read properties of undefined (reading 'X')`). The table "The parts of the extension" says which names of the shell each part leans on. Read the shell's own code for that name in the version that is installed:

**4. Change only that part**, in the sandbox (sandbox_run), on the installed file. Keep the old way working where you can, so the extension still loads on the version before:

## The shared clipboard, for mending it

In the user's words: copy and paste with Windows does not work; I cannot paste from Windows; copied files do not reach Windows; the clipboard is not shared.

`/usr/local/lib/mentor/mentor-clipboard` talks to the launcher on Windows over the virtio port `org.mentor.clipboard` (`/dev/virtio-ports/org.mentor.clipboard`), one JSON object per line: `{"text": "..."}` for text; for copied files `{"files": id, "count": n, "bytes": total}`, then `{"dir": id, "name": path}` and `{"file": id, "name": path, "size": n}` with `{"chunk": id, "data": base64}` as many as needed, then `{"files-end": id}` (or `{"files-cancel": id}`; `{"files-refused": why}` when a copy is too large). It runs on X11 through Xwayland on purpose (`GDK_BACKEND=x11` in its autostart file): a Wayland program sees the clipboard only while it has the keyboard, an X11 one always, and GNOME mirrors the clipboard between the two. So it needs `xorg-xwayland` and GTK 3. Files that arrive are put on the clipboard by `mentor-clipboard-files` (GTK 4). The udev rule gives the logged-in user the two ports.

Check: `pgrep -af lib/mentor/mentor-clipboard` (one line); `ls -l /dev/virtio-ports/` (the two ports, when started by the launcher; on a real computer there are none and the clipboard is simply not shared: `mentor-clipboard` then ends at once, quietly, and `mentor doctor` says "no host to share the clipboard with" instead of checking it); its errors: `journalctl -b --user -o cat | grep -i -A8 mentor-clipboard` (empty when it was never started or its file is gone: then `mentor verify` names the file).

**When copy and paste with Windows stopped**, in this order: `mentor doctor` (line "the clipboard shared with the host"); `mentor verify` (is `mentor-clipboard`, `mentor-clipboard-files`, its autostart file or the udev rule listed?); put back what is listed (the table above: the program is the user's to restore, `sudo mentor restore PATH`; the autostart file and the udev rule are yours); then start it again.

**Start it again** (as the user, run_command; no logout, the user's windows stay):

```
pkill -f 'lib/mentor/mentor-clipboard$'; systemd-run --user --quiet --collect --unit=mentor-clipboard-again -E GDK_BACKEND=x11 /usr/local/lib/mentor/mentor-clipboard
```

The user's systemd already has the desktop's `DISPLAY` and `XAUTHORITY`, so nothing else is needed; started by hand without them it ends at once with a Gtk "display != NULL" error. Good answer: `pgrep -af 'lib/mentor/mentor-clipboard$'` shows one line, and `mentor doctor` says `ok the clipboard shared with the host`. At the next login the autostart file starts it as usual. Then ask the user to copy something in Windows and paste it in Mentor.

## Copy text from the screen

**What the user has.** Shift+Super+T, then drag over any text on the screen (in a picture, a video, a program that does not let them select it). The text is read and put on the clipboard, and a small notification says "Text copied" with its beginning; Ctrl+V pastes it, in Mentor and in Windows. Esc or the right button cancels. A click without dragging takes the whole screen. When there is no text there it says "No text found". You can do the same: the tool `screen_text` (TOOLS.md). Taken from Omarchy's `bin/omarchy-capture-text` (github.com/omacom/omarchy, MIT).

**How it is made.**
1. The key: `00-mentor`, `custom-keybindings/mentor-text`, `binding='<Shift><Super>t'`, `command='/usr/local/bin/mentor capture-text'`.
2. `cmd_capture_text` in `/usr/local/bin/mentor` calls `mentor_tools.capture_text("pick")`, and says how it went with `notify-send --app-name=Mentor`.
3. `capture_text` asks the shell for the area: `org.mentor.Shell.ScreenshotArea` (the same picker as Shift+Super+S), into `$XDG_RUNTIME_DIR/mentor-text-PID.png`, removed afterwards.
4. `read_text` makes the picture twice as large (ffmpeg, lanczos: tesseract is made for 300 dpi scans, a screen's letters are small) and runs `tesseract PICTURE - -l eng+ell` with `OMP_THREAD_LIMIT=1`. That limit matters: with its own threads tesseract took 92 seconds for one screen in the VM, alone 1 second. The languages: those in `~/.config/mentor/text-languages` (`eng+ell+deu`) when it exists, else English, Greek and the language of the user's locale, of those installed (`tesseract --list-langs`). Not every installed one: Gradia brings Afrikaans with it, and Afrikaans read `4471-B` as `44/1-8`.
5. The picture is kept as `$XDG_RUNTIME_DIR/mentor-last-text.png` (memory, only the user's, replaced by the next one, gone at log out), for step "When the copied text came out wrong" below.
6. `clipboard_set` puts the text on the clipboard through the shell: `busctl --user -- call org.gnome.Shell /org/mentor/Shell org.mentor.Shell SetClipboard s TEXT`, which is `St.Clipboard.set_text` in the extension. A program cannot simply do it: GNOME has no data-control protocol for `wl-copy`, and a clipboard owner has to stay running. The shared clipboard passes it on to Windows.

**When the copied text came out wrong** (the user says so: "fix the text I copied", "the Greek came out wrong"). The key itself never sends anything to a model: it stays fast, works without an engine, and what people copy (a password, an account number) is not sent anywhere unasked. When they ask:
1. `screen_text` with `area` `last` and `copy` false. It returns what OCR read and the picture it read it from.
2. Look at the picture and write the text as it really is, line by line, the same words, nothing added.
3. `screen_text` with `set_clipboard` set to that text.
4. Say in one sentence that the corrected text is on the clipboard (Ctrl+V).
If it says no picture is kept, they have logged out since: ask them to press Shift+Super+T and copy it again, then do this. When you read the screen with `screen_text` yourself, the picture comes with it the same way: correct the text from it before you use or copy it.

**Packages.** `tesseract`, `tesseract-data-eng`, `tesseract-data-ell` (Mentor's package list). `tesseract` itself also comes with Gradia (through `python-pytesseract`).

**Another language.** When the user reads text in another language: `package_install tesseract-data-XXX` (XXX: `deu` German, `fra` French, `spa` Spanish, `ita` Italian, `tur` Turkish, `rus` Russian, `ara` Arabic, `chi_sim` Chinese; `package_search tesseract-data` lists them all), then write the languages to use, joined with `+`, into `~/.config/mentor/text-languages` (file_write), for example `eng+ell+deu`. Fewer languages read better: keep to what they use.

**Check.**

| Check | Good answer |
|---|---|
| `tesseract --list-langs` | `eng` and `ell` among them |
| `gsettings get org.gnome.settings-daemon.plugins.media-keys custom-keybindings` | ends with `.../custom-keybindings/mentor-text/` |
| `gdbus introspect --session --dest org.gnome.Shell --object-path /org/mentor/Shell \| grep SetClipboard` | `SetClipboard(in  s text);` |
| `mentor call screen_text '{"area": "screen", "copy": false}'` | `The text read …` and the words on the screen, in about 5 seconds |

**When it does not work.**
- The key does nothing: the user's own `custom-keybindings` list overrides Mentor's (someone added a key of their own). `gsettings get` as above; if `mentor-text` is missing, add `'/org/gnome/settings-daemon/plugins/media-keys/custom-keybindings/mentor-text/'` to the list with `settings_set` (keep every entry that is there).
- "The text could not be copied", and `screen_text` says SetClipboard is unknown: the extension in use is older than the file (a new extension is loaded at the next login): session_logout, or a restart.
- `screen_text` says tesseract is not installed: `package_install tesseract tesseract-data-eng tesseract-data-ell`.
- It reads wrong letters: OCR is never perfect. A larger area around the words, or the text made larger on the screen (Ctrl and + in most programs), helps; so does having only the right languages (above).

Tested headless 2026-10-17: the key and a drag over a text editor and a web page, English and Greek, Esc, an area with no text, a whole screen in about 5 seconds. A line mixing Greek and English can still come out with a word in the wrong alphabet.

## The game mouse

In the user's words: the view does not turn with the mouse in a game; I cannot look around in a game; the pointer is caught in the window.

**What the user has.** In 3D games (shooters such as QC:DE or GZDoom, anything that turns the view with the mouse) the view turns when they move the mouse. Nothing to switch on: it happens by itself while a game is in front **and Mentor is full screen** (Ctrl+Alt+F, or the Full screen switch), and the normal pointer is back as soon as they leave the game or full screen. In a normal window the pointer is never held, a game included (the user's wish, 2026-10-18): it always moves freely between Mentor and Windows, and the view of a game does not turn with it there.

**Why it is needed.** Mentor's window on Windows normally gives the system inside a *tablet*: it says where the pointer is, not how far it moved. That is what makes the pointer glide in and out of Mentor's window with no clicking. A game that holds the pointer (Wayland pointer lock) turns the view by how far the mouse moved, and a tablet never says that: menus work, the view does not move. The *game mouse* is a second pointer (QEMU `virtio-mouse-pci`, "QEMU Virtio Mouse") that only says how far it moved. Only one of the two is in use at a time; the launcher switches.

**How it works.**
1. The shell extension's part `game mouse` (`class GameMouse` in `extension.js`) watches the window in front. It wants the game mouse when the app in front has `Game` in the `Categories` of its desktop file, or its app id is in `games` in `~/.config/mentor/game-mouse.json`, and the overview is not open. `"mode": "on"` there wants it always, `"off"` never; `"auto"` (or no file) is the above.
2. When what it wants changes, it runs `mentor game-mouse --send on` (or `off`) `--front APP-ID`. That sends `{"game-mouse": true}` on `org.mentor.control` and waits up to 5 seconds for the answer, `{"game-mouse": true, "ok": true}`. What came back is kept in `/run/user/UID/mentor-game-mouse.json` (`on`, `front`, `time`, and `error` when it did not work).
3. ## Settings

**What the user has.** GNOME Settings opens and moves between pages without freezing.

**Why it is made so.** On 2026-10-17, Settings froze each time the user left the Mouse & Touchpad page: the page plays small gesture videos, and when it was left GTK's OpenGL context was lost in the VM (`gdk_gl_context_make_current() failed` in the journal, three times, then a window that does not answer). Drawn without OpenGL (`GSK_RENDERER=cairo`) it does not happen, and Settings is plain enough not to need OpenGL.

**How.** Settings is started two ways, and both go through Mentor's wrapper `/usr/local/bin/gnome-control-center`, which sets `GSK_RENDERER=cairo` (unless it is set already) and runs `/usr/bin/gnome-control-center`:
1. From the app grid, the taskbar and the system menu, by D-Bus: its desktop file says `DBusActivatable=true`, so the `Exec` line of a desktop file is never used. `/usr/local/share/dbus-1/services/org.gnome.Settings.service` is found before GNOME's `/usr/share/dbus-1/services/org.gnome.Settings.service` and starts the wrapper.
2. As a command (`gnome-control-center`, the desktop menu's Settings, the agent): `/usr/local/bin` comes before `/usr/bin` in PATH.

Do not put `env GSK_RENDERER=cairo` into a copy of `org.gnome.Settings.desktop` in `~/.local/share/applications`: it does nothing when Settings is started by D-Bus, and the copy hides every later change to GNOME's own file.

**Check.** Open Settings from the app grid. Then `tr '\0' '\n' < /proc/$(pgrep -f -o gnome-control-center)/environ | grep GSK` says `GSK_RENDERER=cairo`. Go to Mouse & Touchpad, then to another page: it answers.

**If Settings freezes anyway.** Read `journalctl -b -o cat _COMM=gnome-control-center | tail -20`. If `GSK_RENDERER` is not in its environment (the check above), one of the two files is missing: `sudo mentor restore /usr/local/bin/gnome-control-center /usr/local/share/dbus-1/services/org.gnome.Settings.service` (the user runs it), then close Settings and open it again. No logout is needed, though `mentor restore` says "at the next login": both files are read each time Settings starts.

Without opening a window, these say the fix is in place (as the user): `mentor verify` does not list either file; `grep Exec /usr/local/share/dbus-1/services/org.gnome.Settings.service` says `Exec=/usr/local/bin/gnome-control-center --gapplication-service`; `grep GSK /usr/local/bin/gnome-control-center` shows `GSK_RENDERER` set to `cairo`; `command -v gnome-control-center` says `/usr/local/bin/gnome-control-center`. Written to `~/.local/share/icons/Mentor-pointer-white` and `Mentor-pointer-accent-KEY` (with `index.theme`, `Inherits=Adwaita`, and `made-from`, which says what it was made from: it is made again when Adwaita changes), about half a second, then `org.gnome.desktop.interface cursor-theme` is set to that name; the size is `cursor-size`. Only one accent pointer is kept. mentor-chat runs `mentor_pointer.follow_accent()` when `accent-color` changes (`follow_colors`). From a command: `mentor pointer` (says), `mentor pointer white`, `mentor pointer accent --size 48`.

**Check.** `mentor pointer` says the color and size; `gsettings get org.gnome.desktop.interface cursor-theme` is `'Adwaita'`, `'Mentor-pointer-white'` or `'Mentor-pointer-accent-orange'` (and so on); that folder is in `~/.local/share/icons` with a `cursors` folder of about 60 files.

**Two pointers in Mentor's window** (since 2026-10-19; the user, size 48 at 150%): the virtual graphics card holds a pointer of at most 64 by 64 pixels; a larger one (the size times the screen's scale: 48 × 1.5 = 72) GNOME draws into the picture itself ("Can't handle cursor size 72x72" in `journalctl -b -o cat _COMM=gnome-shell`), and the card's last pointer stayed on screen beside it. The extension's part `pointer fits` (only with `virtio_gpu`, `/sys/module/virtio_gpu`) keeps `cursor-size` at the largest of the sizes that is not above the user's choice and fits in 64 pixels at the largest scale (48 at 150% → 36, 54 pixels), on every change of the monitors; with a smaller scale the choice comes back. The user's choice is `~/.config/mentor/pointer-size` (written by `mentor_pointer.apply`, and by the part when `cursor-size` is changed elsewhere, GNOME Settings' Accessibility); `mentor_pointer.current()` reads it, so Mentor Settings shows the size chosen, not the one fitted. Check: `cat ~/.config/mentor/pointer-size` and `gsettings get org.gnome.desktop.interface cursor-size`, their product with the scale under 64; no new "Can't handle cursor size" after the moment of a change. Mentor Settings' Size slider offers only the sizes that look different at the zoom it is opened at (`mentor_pointer.fitting(scale)`: at 150% 24, 30 and 36), and says "Larger sizes at a smaller zoom (now 150%)": the larger steps were all fitted to the same size (the user, 2026-10-19). At a fractional zoom GNOME draws the pointer into the picture itself even when it fits (seen at 125%, 2026-10-19); that is GNOME's way and leaves no second pointer: only the "Can't handle" path did.

**When it is wrong.** The pointer is the old one after a change: programs started before take it when opened again; the shell takes it at once. An accent pointer of the wrong color: `mentor pointer accent` makes it again. A pointer that looks broken after a GNOME update: delete `~/.local/share/icons/Mentor-pointer-*` and choose the color again (it is made from the new Adwaita). If Adwaita's pointer ever comes in another form (no `Xcur` files), `_recolor` leaves the files as they are: the pointer is then Adwaita's in every color, and `mentor_pointer.py` must learn the new form.

## Restarts while Mentor works

**What the user has.** Nothing that restarts or logs out cuts the assistant off without a warning (the user's wish, 2026-10-19):
- **Update** (the green card in the chat, or Mentor Settings, Updates) while the assistant works: a dialog "Mentor is still working" says what it is working on and that a restart now would stop it halfway, with **Update when it's done** (the default) and Not now. With the first, Mentor waits, and when the work is done it asks the usual restart question.
- GNOME's **Log Out**, **Restart** and **Power Off** (the top right menu), and the assistant's own session_logout and restart tools: GNOME's end-session dialog says "Some applications are busy or have unsaved work" and lists "Mentor Assistant: Still working. Please wait." before Log Out (a longer reason is cut off there).

**How.** mentor-chat: `busy_work` (the titles of the tabs the assistant is busy in), `hold_session` (called from `on_busy_changed`) takes GNOME's session inhibitor while any tab is busy, `org.gnome.SessionManager.Inhibit` with the app's id `org.mentor.Chat` and flag 1 (log out), and lets it go (`Uninhibit`) when none is (asked directly: `Gtk.Application.inhibit` gave no app id, and GNOME's dialog then listed nothing, tested 2026-10-19); `install_update` shows the dialog and keeps the request in `update_after`, which `on_busy_changed` carries out when the last tab is done. Mentor Settings (`install_update`): the same dialog; it knows the assistant is busy from its engine's process (`agent_busy`) and looks again every 5 seconds. The update itself (`mentor-update-apply.service`) restarts as root and is not held by the inhibitor: the two dialogs are what keeps it from cutting the work.

**Check.** While the assistant works: `gdbus call --session --dest org.gnome.SessionManager --object-path /org/gnome/SessionManager --method org.gnome.SessionManager.IsInhibited 1` says `(true,)`, and `gdbus call --session --dest org.gnome.SessionManager --object-path /org/gnome/SessionManager --method org.gnome.SessionManager.GetInhibitors` lists one whose reason is "Still working. Please wait." (`GetAppId` on it says `org.mentor.Chat`). When it is done, `(false,)` (unless another program holds the session).

**When it is wrong.** No warning at logout while the assistant works: the inhibitor did not take; `journalctl --user -b -o cat | grep -i inhibit` and the check above. The warning stays when nothing works: a tab still marked busy (its gear turning); Stop in that tab clears it. The update never comes after "Update when it's done": the chat must be running (it waits, not Mentor Settings once closed); press Update again.

## Shutdown

**What the user has.** A shutdown or restart never waits more than 30 seconds for a program that does not stop; it is then stopped by force. GNOME's own wait is 90 seconds: once, at the restart right after systemd itself was upgraded (262 to 262.1), the screen stayed black 85 seconds (2026-10-19). The user chose 30 seconds over 15.

**How.** `/etc/systemd/system.conf.d/90-mentor-stop-timeout.conf` and `/etc/systemd/user.conf.d/90-mentor-stop-timeout.conf`: `DefaultTimeoutStopSec=30s`, for the system's services and the user's own. systemd also gives it to `systemd-shutdown` for the last programs left. A unit with its own `TimeoutStopSec=` keeps it. Updates (Mentor's, and the system's through `system_upgrade`) are installed before the shutdown begins, so this does not cut them.

**Check.** `systemctl show -p DefaultTimeoutStopUSec` and `systemctl --user show -p DefaultTimeoutStopUSec` say `30s` (after the next start). A slow restart: `journalctl --list-boots` and the time between one boot's last entry and the next one's first (about 15 seconds is usual); the end of the earlier boot (`journalctl -b -1 | tail -40`) shows what was stopping, though the very last wait comes after the log is closed.

**When it is wrong.** A program that needs longer to stop cleanly (a database writing much at once) is cut: give its unit its own `TimeoutStopSec=` in a drop-in, not a longer default.

## Keyboard layouts

**What the user has.** With more than one keyboard layout (Settings, Keyboard, Input Sources; for example English and Greek), **Alt+Shift** switches to the next one, as on Windows, and so does GNOME's **Super+Space**. Alt+Shift switches when the two are let go with no other key in between, so Alt+Shift+Tab, Alt+Shift+F and the like stay shortcuts of the programs.

**How.** `mentor-emergency-key` (root, it reads the keyboards below GNOME for Ctrl+Alt+Backspace too) sees Alt and Shift go down together with nothing else held, and when one of them goes up without another key pressed meanwhile, it asks the desktop of the session in front (`loginctl`, seat0, a graphical one) through D-Bus as that user: `org.mentor.Shell.NextInputSource` of Mentor's extension, which calls GNOME's own switcher (`getInputSourceManager()._modifiersSwitcher()`, the one GNOME's layout-switch keys use; the top bar's indicator follows). With one layout it does nothing. GNOME's own option `grp:alt_shift_toggle` is not used: it switches as the keys go down, and took Alt+Shift+Tab and Alt+Shift+F along (tested 2026-10-18). On the text consoles nothing is switched.

**Check.** With two layouts: `gsettings get org.gnome.desktop.input-sources mru-sources` changes order after Alt+Shift, and not after Alt+Shift+F. `journalctl -u mentor-emergency-key` says "could not switch the layout" if the call failed. The extension's method: `gdbus call --session --dest org.gnome.Shell --object-path /org/mentor/Shell --method org.mentor.Shell.NextInputSource`.

**When it does not work.** `systemctl is-active mentor-emergency-key` (it must run); `xkb-options` should hold no `grp:` option, which would switch a second time; a shell that renamed `_modifiersSwitcher` breaks only this method (the shell's code: `shell_source` search `_modifiersSwitcher`).

## Animations

**What the user has.** Windows, the overview and menus open and close with GNOME's short animations, drawn by the graphics card. Measured on 2026-10-18 (Radeon 860M, Mentor.exe's display): the window shows about 118 frames a second on a 120 Hz screen, and opening and closing the overview over and over costs the shell about 12 % of one processor core while it moves (2 % with animations off), nothing when the screen is still.

**How.** `00-mentor` has `enable-animations=true` (until 2026-10-18 false, from the time the VM had no 3D). The extension's part `animations` holds them back for the session, without touching the user's setting, when the screen is drawn without a graphics card: a virtio-gpu whose feature bit 0 (`VIRTIO_GPU_F_VIRGL`, the first character of `/sys/bus/virtio/devices/*/features`) is 0, which is the launcher's Graphics card switch off; or no `/dev/dri/renderD*` at all. Note: the render node exists even without 3D, so the bit is what tells. A PC with a real graphics card keeps them.

**Check.** `gdbus call --session --dest org.gnome.Shell --object-path /org/mentor/Shell --method org.mentor.Shell.Status` has `"animations": "on"` (or why not). A user who wants none: `gsettings set org.gnome.desktop.interface enable-animations false` (Settings, Accessibility, Reduce Animation); that is theirs and wins.

## Memory

**What the user has.** When memory runs short, what has not been used for a while is compressed in memory itself (zram) instead of a program being closed; Chromium puts tabs to sleep that have not been looked at for a while (Memory Saver, table above). Together they keep many open tabs from slowing the desktop down.

**How.** `zram-generator` (package) reads `/etc/systemd/zram-generator.conf` at every start and makes `/dev/zram0`: half the memory, at most 8 GB, compressed with zstd, swap priority 100. `/etc/sysctl.d/90-mentor-zram.conf` sets `vm.swappiness` 180 and `vm.page-cluster` 0 (moving a page into compressed RAM is cheap) and the watermarks Fedora uses. There is no swap on the disk. The freeze watch (FREEZES.md) still closes the largest app when memory runs out even so.

**Check.** `swapon --show` lists `/dev/zram0`; `zramctl` shows how much is in it and how small it became (DATA against COMPR); `sysctl vm.swappiness` says 180.

**When it is wrong.** No `/dev/zram0`: `pacman -Q zram-generator`, then `systemctl status systemd-zram-setup@zram0`. To turn it off (a user who wants no swap): remove the `[zram0]` section, `systemctl daemon-reload`, `swapoff /dev/zram0`; in the sandbox, as every system change.

## Languages

**What the user has.** Settings, System, Region & Language, Language lists about 37 languages: English (US and UK), German, French, Spanish, Italian, Portuguese, Dutch, Polish, Czech, Slovak, Slovenian, Croatian, Hungarian, Romanian, Bulgarian, Greek, Russian, Ukrainian, Turkish, Swedish, Danish, Norwegian, Finnish, Estonian, Latvian, Lithuanian, Japanese, Chinese, Korean, Arabic, Hebrew, Indonesian and Thai. Choosing one changes GNOME and its apps after a log out.

**How.** GNOME's translations come with its packages, all of them. A language is only listed once its locale is made: `mentor-enable` (run by the image build and by every update) uncomments those languages' `xx_YY.UTF-8 UTF-8` lines in `/etc/locale.gen` and runs `locale-gen`.

**Mentor's own words stay English**: the chat's buttons and cards, Mentor Settings and the desktop menu. The assistant itself answers in the user's language. Say so when a user changes the language.

**When the user asks for a language.**
1. If it is in the list above: tell them: "Open Settings, System, Region & Language, Language, choose it, then log out and in again." Or set it for them through AccountsService (`busctl call org.freedesktop.Accounts /org/freedesktop/Accounts/User$(id -u) org.freedesktop.Accounts.User SetLanguage s de_DE.UTF-8`, which asks for the password), then ask them to log out.
2. If it is not listed: find its line with `grep -n "xx_YY" /etc/locale.gen` (some have no `.UTF-8` in the name, for example `hi_IN UTF-8`). Uncomment it and run `locale-gen` as root, in the sandbox, and apply. Then do step 1.
3. Check: `localectl list-locales` lists it.

**Folders.** The folders in the home folder (Desktop, Documents, Downloads, Pictures...) keep their English names in every language. GNOME would ask after a change of language whether to rename them into it; that question is switched off (`mentor-enable`: `systemctl --global mask user-dirs-update-gtk.service`), because Mentor's recipes live in `~/Documents/Mentor recipes` and after a rename Mentor would look in a new, empty Documents. Mentor's tools that read and write the user's words in other languages (recipes, web apps, reminders) do not depend on the language; `mentor doctor` reads the programs it asks in English (`LC_ALL=C.UTF-8`), so it says the same in every language. A user who wants the folder names in their language anyway: `systemctl --global unmask user-dirs-update-gtk.service` as root, log out and in, and say yes to the question; tell them first that Mentor's recipes then have to be moved back to `~/Documents/Mentor recipes`.
